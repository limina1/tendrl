* Core Pattern: Modular Nostr Engine

Both systems follow the same fundamental pattern:
#+begin_example
Fetch Events → Store in Database → Query & Enrich → Render with Templates
#+end_example

** nostr-feeds Pattern (Original)
#+begin_src
nak (fetch) → SQLite (store) → Python (enrich) → Jinja2 (render)
#+end_src

** Tendrl Pattern (Evolution)
#+begin_src
nostrdb/notedeck (fetch) → nostrdb/LMDB (store) → Rust/Python (enrich) → Jinja2 (render)
#+end_src

* Component-by-Component Comparison

** 1. Event Fetching

*** nostr-feeds: nak CLI
- Uses ~subprocess.run(['nak', 'req', ...])~
- Generates filter commands dynamically
- Returns JSONL from relays
- Simple, reliable, program-agnostic

- Uses nostrdb's built-in query engine

- Native LMDB storage (not SQL)
- Tags stored in nostrdb's internal format
- Queried through Rust FFI bindings

** 3. Tag Handling

*** nostr-feeds: JSON Serialization (WORKS)

Storage (db.py:640):
#+begin_src python
tags_json = json.dumps(event.get('tags', []))
# Result: '[["p", "abc123..."], ["e", "def456..."]]'
#+end_src

Retrieval (db.py:427):
#+begin_src python
if 'tags_json' in event and event['tags_json']:
    event['tags'] = json.loads(event['tags_json'])
    # Result: [["p", "abc123..."], ["e", "def456..."]]
#+end_src

*** Tendrl: nostrdb Native (BROKEN)

The bug is somewhere in this pipeline:
1. ~tendrl_ingest~ reads JSON event
2. Calls nostrdb FFI to store event
3. nostrdb stores to LMDB
4. ~tendrl_query~ reads from LMDB
5. Serializes back to JSON
6. **Tag values are missing!**

Possible causes:
- nostrdb's C API doesn't preserve all tag values
- FFI binding loses data during conversion
- Query serialization bug
- LMDB schema limitation

** 5. Query & Enrichment

*** nostr-feeds: Python-based

#+begin_src python
# Query by tag (uses LIKE on JSON string)
def get_events_by_tag(conn, kind, tag_type, tag_value, limit):
    like_pattern = f'%["{tag_type}", "{tag_value}"%'

    query = """
        SELECT * FROM events
        WHERE kind = ? AND tags_json LIKE ?
        ORDER BY created_at DESC LIMIT ?
    """

    cursor = conn.execute(query, (kind, like_pattern, limit))
    return [parse_event_row(row) for row in cursor.fetchall()]
#+end_src

**Works because**: Tags are stored as JSON strings, so LIKE pattern matching finds them.

*** Tendrl: Rust/nostrdb

Query filters built in Rust, executed against LMDB, returned as JSON.

The query engine works, but the JSON serialization is buggy.

** 6. Rendering

Both use Jinja2 templates - this part is identical.

* Root Cause Analysis

** Why nostr-feeds Works

1. **Explicit serialization**: ~json.dumps(tags)~ → store as TEXT
2. **Explicit deserialization**: ~json.loads(tags_json)~ → Python list
3. **Simple data flow**: JSON in → TEXT storage → JSON out
4. **No FFI layer**: Pure Python/SQLite

** Why Tendrl is Broken

1. **Implicit serialization**: Relies on nostrdb's internal format
2. **FFI boundary**: Rust ↔ C ↔ nostrdb ↔ LMDB
3. **Data loss somewhere in**:
   - ~tendrl_ingest~ storing to nostrdb
   - nostrdb's LMDB storage format
   - ~tendrl_query~ reading from nostrdb
   - JSON serialization back to client

** The Smoking Gun

#+begin_src bash
# Event has 533 p-tags according to count
./tendrl_query --kinds 3 --author dc4cd086... | \
  jq '.tags | map(select(.[0] == "p")) | length'
# Output: 533 ✓

# But all tags are empty!
./tendrl_query --kinds 3 --author dc4cd086... | \
  jq '.tags[:3]'
# Output: [["p"], ["p"], ["p"]] ✗
#+end_src

The tag *count* is preserved, but the *values* are stripped.

This suggests the bug is in the **query/serialization layer**, not the storage layer.

** Option 2: Workaround with nak (Quick Fix)

Bypass nostrdb for follow list:
#+begin_src bash
# Fetch follows directly from relays
nak req -k 3 -a dc4cd086... wss://relay.damus.io | \
  jq -r '.tags[] | select(.[0] == "p") | .[1]' > my_follows.txt

# Use for filtering
while IFS= read -r pubkey; do
  FOLLOW_FILTER="$FOLLOW_FILTER --author $pubkey"
done < my_follows.txt

nak req -k 1 $FOLLOW_FILTER --limit 50 wss://relay.damus.io
#+end_src

** Option 3: Hybrid Approach

Use nostrdb for event storage but nak for querying:
- Keep ~tendrl_ingest~ for fast batch imports
- Use ~nak req~ with filters for actual queries
- Render with existing Jinja2 templates

This combines the speed of nostrdb storage with the reliability of nak querying.

* Key Takeaways

1. **nostr-feeds architecture is proven**: 3 years of production use
2. **SQLite + JSON strings is reliable**: Explicit serialization works
3. **nostrdb is faster but complex**: FFI layer introduces bugs
4. **Tendrl's goal is valid**: Using notedeck's engine is more efficient
5. **The bug is fixable**: It's in the query layer, not the design

The pattern evolution from ~nak + SQLite~ to ~nostrdb + notedeck~ is sound.
The implementation just needs debugging in the tag serialization code.
