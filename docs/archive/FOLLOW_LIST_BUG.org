* Possible Root Causes

**UPDATE**: After analyzing nostr-feeds architecture (see ~ARCHITECTURE_COMPARISON.org~), the root cause is narrowed down:

1. *Bug in ~tendrl_query~*: Query serialization drops tag values (MOST LIKELY)
   - Tag *count* is preserved (533 tags detected)
   - Tag *values* are stripped (only ~["p"]~ returned, not ~["p", "pubkey"]~)
   - Suggests bug in JSON serialization layer, not storage

2. *Bug in nostrdb FFI binding*: Rust↔nostrdb tag array conversion
   - Tags stored correctly (ingest doesn't error)
   - Tags retrieved incorrectly (query strips values)
   - FFI boundary may lose array elements

3. *Bug in ~tendrl_ingest~*: Event import strips tag values during storage (UNLIKELY)
   - Would affect tag count too

4. *nostrdb limitation*: Database schema doesn't preserve all tag values? (UNLIKELY)
   - ~primus/notedeck~ successfully uses nostrdb

* Notes
The bug blocks core follow-filtering functionality. The event is stored (50MB nostrdb) but tag values are lost when queried back. This appears to be a fundamental issue with the tendrl_ingest/tendrl_query pipeline or nostrdb FFI bindings.

* Architecture Context

See ~ARCHITECTURE_COMPARISON.org~ for detailed analysis of how this differs from the working ~nostr-feeds~ implementation.

**Key Difference**: nostr-feeds stores tags as JSON strings (~json.dumps()~) in SQLite TEXT column, then deserializes (~json.loads()~) on retrieval. This explicit serialization works reliably.

Tendrl uses nostrdb's native LMDB storage, which should be faster but has a bug in the query/serialization layer that strips tag values.
